# Sensitive Data Governance Test Catalog

**Companion assessment:** [Security governance audit](SECURITY_GOVERNANCE_AUDIT.md)  
**Use:** Acceptance criteria for a synthetic, isolated test environment. These are security tests, not production extraction instructions. Do not run data-export cases against live customer/employee/health data without written approval.

## Classification and validation conventions

| Class | Meaning for this catalog |
|---|---|
| **Public** | Explicitly approved for public release; otherwise not public by default. |
| **Internal** | Routine operational information limited to workforce/platform users. |
| **Confidential** | Non-public commercial, financial, investigative, or transaction information. |
| **Restricted** | Identifiable personal, customer, employee, or account-linked data requiring purpose/role controls. |
| **Highly Restricted** | Authentication/payment secrets, government identifiers, identity documents, or health data; deny/minimize by default. |

Expected mask patterns: **Aadhaar** `XXXX-XXXX-1234`; **Indian PAN/tax ID** `ABCXX1234X`; **account number** `XXXXX6789`; **card number** `XXXX-XXXX-XXXX-1234`; **phone** `XXXXXXX789`; **email** `j***@example.com`; **address** city/region only; **passport/identity document** never return image/document contents; **CVV/CVC** never store or return. Do not treat a format mask as permission to retrieve.

For every case, a pass requires the expected control at the API/data layer, across direct API calls, query results, prose, charts, exports, saved history, replay, and errors. A frontend warning alone is a fail. The application has not yet been run against this full catalog; the baseline column reports only the limited static detector probe where applicable.

## Suggested automated assertions

For every role/domain combination, assert all of the following:

1. The decision is made by the backend; client-side UI changes do not alter authorization.
2. Every row and joined tenant-scoped table is constrained to the authenticated domain.
3. Unknown or unclassified columns fail closed; `SELECT *`, hidden columns, aliases, expressions, nested JSON, and narrative text do not bypass the policy.
4. CVV/CVC is absent from query permissions, model context, API responses, result tables, saved history, logs, exports, and error messages.
5. PII masks match the approved patterns exactly and no sensitive value can be reconstructed through repeated filters or aggregations.
6. History, replay, chart tooltips, CSV downloads, and cached results apply the same controls as the initial response.
7. Every allow, deny, mask, replay, export, and HITL action produces a unique, append-only server audit event with actor, role, domain, purpose, policy version, and outcome.
8. An analyst cannot view or change another user's HITL item; an authorized reviewer can, with reason and immutable audit evidence.
9. SQL is parsed and constrained against approved tables, columns, functions, tenant predicates, complexity budgets, and result limits before execution.
10. A regression run includes both expected legitimate aggregates and adversarial paraphrase/encoding/Unicode cases; all pass/fail results are attached to a release record.
